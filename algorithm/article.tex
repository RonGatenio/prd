Nonvolatile Memory (NVM) technologies offer new avenues for building high-performance and crash-consistent applications by combining byte-addressable DRAM-like characteristics with non-volatility. However, these features introduce complex challenges in ensuring data consistency, especially under concurrent access scenarios.

This paper introduces \SignRaceDetector, a specialized tool designed to detect {\NameRace}s—specific type of concurrency bugs in PM environments that can lead to critical inconsistencies following system failures.
\SignRaceDetector utilizes graph-theoretical analysis along with happens-before and program-dependence analysis to map causal relationships and dependencies among program operations. While these analyses are well-established techniques in data-race detection, \SignRaceDetector efficiently generalizes across multiple thread interleavings to detect potential races within a single program execution, significantly enhancing the speed and efficiency of race detection in NVM environments.

\section{Introduction}

Nonvolatile Memory (NVM) technologies, such as Intel's Optane DC Persistent Memory \cite{intel2019optane} or Compute Express Link (CXL) attached SSDs\todo{Add cite, Kioxia + Jungi Jeong and Changhee Jung. 2021. PMEM-Spec}, represent a significant advancement in computer memory design, offering a unique combination of byte-addressable access and DRAM-like performance with the added benefit of non-volatility. These characteristics open new avenues for building high-performance, crash-consistent applications that maintain data integrity across power failures and system crashes. However, the integration of NVM into existing computing paradigms introduces new complexities, particularly in ensuring data consistency across volatile and persistent memory layers.

% TODO: eADR might require very specific hardware. read about this. Will it work with CXL?
Optane with Asynchronous DRAM Refresh (ADR) doesn't guarantee the persistence of cache contents during a power failure. This limitation requires programmers to explicitly ensure that critical data is flushed from the CPU cache to the persistent memory. Technologies like Optane eADR \cite{intel2021optane_eadr} promise to address these issues by ensuring cache persistence, but they are not yet widespread. Therefore, developers must continue to support the more common Optane ADR. Future hardware technologies might integrate eADR features, reducing the burden on developers, but this is not clear at this time.

Ensuring data persistence in NVM involves using an Application Binary Interface (ABI) that provides instructions for flushing memory to the cache. On Intel architectures \cite{intel2020abi}, instructions like Cache Line Write Back (CLWB) and Store Fence (SFENCE) are used. CLWB writes modified cache lines back to memory without invalidating them, ensuring that the data is persisted. SFENCE ensures that all store instructions before the fence are completed before any subsequent store instructions. These operations are critical for ensuring that needed data is stored in persistent memory but are expensive in terms of performance. As a result, programmers strive to minimize their use, which can inadvertently lead to concurrency bugs.

This work targets a specific concurrency-related bug prevalent in NVM programs, originally identified as \textit{\NamePMRaceRace} by Chen, Zhangyu, et al. \cite{pmrace2022}. This bug occurs when one thread writes to persistent memory (PM) data that is based on volatile data currently in cache. Such scenarios can cause inconsistent NVM states post-crash, if the system crashes before the read location is persisted. Throughout this paper, we refer to this bug as \textit{\NameRace}.

Specifically, a \NameRace starts when a thread writes data to PM but gets interrupted before the data is explicitly written to the PM. Next, another thread reads this volatile data and uses it to modify another memory location. Finally, this latter modification is persisted to memory before the original data does. This sequence of events can create an inconsistent memory state, and we denote it a \textit{\NameRace}.

To illustrate the detrimental effect the persistency bug may have, consider Harris's Linked-List \cite{harris2001}. In this data structure, the insert operation involves creating a new node, linking it to the next node, and then using an atomic operation to link the previous node to the new node. Now, imagine that another thread attempts to insert a node immediately after the newly inserted node and succeeds. Even if an explicit flush operation is added at the end of the insert operation to ensure persistence, thread interleavings could still cause issues. Specifically, the first insert operation might be interrupted just before the flush, while the second insert operation completes entirely. If a crash occurs at this moment, the system might recover to a state where neither node appears in the list, even though the second operation had seemingly completed. This example demonstrates how \NameRace conditions can lead to significant inconsistencies, as operations that were completed might be lost if their persistence wasn't properly managed.

Chen, Zhang, Hua, and Ding \cite{pmrace2022} introduced PMRace, a specialized tool for identifying crash-consistency bugs in persistent memory (PM) applications, targeting \NamePMRaceRace. PMRace employs PM-aware coverage-guided fuzz testing to explore various execution interleavings that could reveal hidden inconsistencies. By instrumenting the target application, PMRace captures information on PM-specific operations. Each run of the tool focuses on a specific set of conditions and is likely to detect only one bug, requiring multiple runs to comprehensively identify all potential issues. This approach sets a benchmark for bug detection in concurrent PM systems but can be resource-intensive and time-consuming.

In this paper, we introduce \NameRaceDetector (\SignRaceDetector), a tool designed to effectively identify and diagnose \NameRace conditions in PM environments. \SignRaceDetector extends well-established techniques from data-race detection, such as happens-before analysis. Additionally, it uses program-dependence analysis to detect data dependencies among operations. \SignRaceDetector uses a \HBGName ($\HBG$) and a \PDGName ($\PDG$), to analyze the execution trace of the program and identify {\NameRace}s. \SignRaceDetector provides good coverage of {\NameRace}s at a much lower cost. \todo{When there are numerical results, the speedup should be presented here}

The happens-before analysis, commonly used in traditional data-race detection, plays a crucial role in our approach. It helps establish the temporal and causal relationships between program events by creating a partial order of events based on synchronization primitives. This technique enables us to analyze multiple equivalent interleavings of program execution within a single run, ensuring that a single execution of \SignRaceDetector can identify a \NameRace in all executions that yield the same \HBGName.
However, the precision of this generalization technique is heavily dependent on the accuracy of the happens-before analysis. The fewer happens-before relationships we recognize, the more potential races, including false positives, we will detect. This is because, without recognizing these relationships, all read and write operations would be considered as happening in parallel, leading to an expanded detection of races.

\SignRaceDetector works by first instrumenting the program to log memory operations and synchronization events, capturing a detailed execution trace. This trace is then analyzed to construct a comprehensive model of the program's execution. Next, \SignRaceDetector builds a \HBGName ($\HBG$) based on the recorded relationships between operations, and a \PDGName ($\PDG$) identifying dependencies based on data flow. Finally, \SignRaceDetector combines these analyses to pinpoint potential \NameRace conditions. Optimization techniques are applied to handle large traces efficiently to achieve scalable and practical detection process for real-world applications.

\SignRaceDetector achieves comprehensive coverage of possible race conditions while significantly enhancing the speed and efficiency of race detection in NVM programs. This approach eliminates the need for a large number of individual test runs, making the detection process more practical and resource-efficient.

\subsection{Persistent Memory Programming}
% \todo{introduction and explanation about persistent memory programming paradigms, technologies, and their applications}
Persistent Memory (PM) represents a significant advance in memory technology by combining the durability of storage devices with the byte-addressability of traditional RAM. This unique characteristic allows applications to directly access and manipulate data in memory using byte-level load and store instructions, circumventing the page cache and offering performance akin to DRAM.

However, the intrinsic non-volatility of PM, such as that found in technologies like 3D XPoint, introduces additional complexities in programming, especially concerning crash consistency. Data in PM persists through power outages, presenting challenges in ensuring data consistency if a system crashes. Unlike PM, CPU caches can be volatile and may not automatically preserve data upon power failure. This discrepancy necessitates managing the order of data persistence, which hinges on how cache lines are evicted—either through automatic system processes or explicit flush operations.

Programming for PM must carefully manage these aspects to maintain data integrity and system consistency after crashes. Developers can use high-level programming constructs like logging or copy-on-write (CoW) mechanisms to enforce crash consistency, but these methods often come with significant performance overheads. As a lower-level alternative, specific instructions such as CLWB (Cache Line Write Back) and SFENCE (Store Fence) in the x86 instruction set, or DC CVAP (Clean Cache Line to Point of Persistence) and DSB (Data Synchronization Barrier) in ARM \cite{arm2020abi}, provide direct control over cache line flushing and memory ordering. These tools help ensure that writes are properly ordered and visible before subsequent operations.
However, synchronization primitives like these can be performance-intensive, leading programmers to minimize their use whenever possible.

Furthermore, non-temporal store instructions offer another method by directly writing data to PM, bypassing the volatile CPU caches. While this approach avoids caching overheads, it eliminates the benefits of fast data retrieval for frequently accessed ("hot") data, making it less suitable for such use cases.

Overall, effective PM programming requires a deep understanding of both the underlying hardware features and the software techniques necessary to exploit this technology fully while ensuring robust crash consistency.

\subsection{Happens-Before}
The happens-before relationship, originally formulated by Leslie Lamport \cite{lamport1978}, determines the causal ordering of events in a program execution. It is commonly used to reason about the sequence and dependencies of operations in concurrent and distributed systems and is a prominent concept in data race detection algorithms.
The basic idea is that a pair of events \((e_i, e_j)\) are related if communication between processes allows information to be transmitted from \(e_i\) to \(e_j\).
This concept was initially defined by Lamport for distributed systems, and it can be adapted to multi-threaded programs by treating threads as processes and the events observed by our race detector as the events occurring in the system.

The happens-before relationship is a partial order on the events of a particular execution of a multi-threaded program and can be understood through the following principles. First, within a single thread, the order of instructions as written in the program code defines the happens-before relationship. If instruction \(A\) appears before instruction \(B\) in the same thread, then \(A\) happens-before \(B\). Second, synchronization operations such as acquiring and releasing locks, spawning and joining threads, syncronized atomic reads and writes to the same memory address, and other inter-thread communication mechanisms establish additional happens-before relationships across threads. For instance, if thread \(T1\) releases a lock and subsequently thread \(T2\) acquires the same lock, then all operations in \(T1\) that happened-before the release are considered to happen-before any operations in \(T2\) after the lock acquisition. Lastly, the relation is transitive, so if \(A\) happens-before \(B\) and \(B\) happens-before \(C\), then \(A\) happens-before \(C\).

\myparagraph{Happens-Before Graph}
From the happens-before relationship, we can derive a happens-before graph (HBG). In this graph, each executed instruction is represented as a node, and directed edges between these nodes create a partial order that outlines the execution order between instructions. Specifically, if an event \(A\) happens-before an event \(B\), then there is a directed path from \(A\) to \(B\) in the graph.
The HBG is particularly useful for visualizing and analyzing concurrent executions, as it decouples the execution order from the actual timing of instructions. Consequently, different executions that may run at varying speeds but share the same happens-before graph are considered behaviorally equivalent, reflecting consistent execution behavior despite temporal differences. This abstraction helps in identifying potential concurrency issues like data races and ensures a consistent understanding of the execution order.

\myparagraph{Vector Clocks}
Vector clocks, based on Lamport's timestamps \cite{lamport1978} and further developed by Fidge \cite{fidge1987vc} and Mattern \cite{mattern1988vc}, are a widely used method to capture the causality between events in parallel and distributed systems and to determine the happens-before partial order between them. They are commonly used in data race detection algorithms.
In our algorithm, we rely on the concept of vector clocks to reason about the temporal state of each event in the HBG.

A vector clock is a data structure that keeps track of the logical time of events in a distributed system. It is represented as an array of counters, where each counter corresponds to a process or thread in the system. Each process maintains its own vector clock, which it updates according to specific rules: each process increments its own counter before issuing an event. When a process sends a message, it includes its current vector clock with the message. Upon receiving a message, a process updates its vector clock by taking the element-wise maximum of its own vector clock and the received vector clock.

Intuitively, vector clocks represent the known state of execution across all threads from the perspective of a single event. If event \(A\) has a vector clock value of \(V_A\) and event \(B\) has a vector clock value of \(V_B\), then \(A\) happens-before \(B\) if and only if \(V_A\) is element-wise less than \(V_B\). This property allows vector clocks to efficiently capture and compare the causal relationships between events.

By using vector clocks, we can precisely track the happens-before relationships across all events in a system, which is crucial for detecting concurrency issues and understanding the execution flow of parallel and distributed programs. This detailed tracking helps in ensuring consistency and correctness in the presence of concurrent operations.

\subsection{Program Dependence Analysis}
Program dependence is a relation between two instructions or statements, \(S1\) and \(S2\). This relation exists if the outcome of \(S1\) directly influences the outcome of \(S2\), necessitating that \(S1\) be executed before \(S2\) to ensure correct program behavior.
There are two types of program dependence: data dependence and control dependence.

Data dependencies arise between two operations when the output of one operation is required as input for the other. For instance, if \(S1\) computes a value that \(S2\) uses, there is a data dependency from \(S1\) to \(S2\). For example:
\begin{verbatim}
S1: x = 5;
S2: y = x + 1;
\end{verbatim}
In this case, \(S2\) is dependent on \(S1\) because \(S2\) uses the value of \texttt{x} computed by \(S1\).

Control dependencies exist when the execution path of one operation depends on the outcome of a conditional branch affecting another operation. Specifically, \(S1\) controls the execution of \(S2\) if the decision to execute \(S2\) is based on a condition evaluated in \(S1\). For example:
\begin{verbatim}
if (condition) {
    S1;
}
S2;
\end{verbatim}
Here, the execution of \(S1\) is control-dependent on the evaluation of the `condition`. If the condition is true, \(S1\) will execute; otherwise, it will not. \(S2\) is not directly control-dependent on the `condition`.

The \PDGName (\(\PDG\)) \cite{pd1988} is a directed, acyclic graph that models the execution flow of a program as a partial order. Each node in the \(\PDG\) corresponds to an executed instruction, and directed edges illustrate the dependencies between these instructions. The \(\PDG\) helps visualize and analyze these dependencies, making it easier to understand how different parts of a program interact. By representing both data and control dependencies, the \(\PDG\) provides a comprehensive view of the execution flow, which is used to optimize compilers, verify programs, and analyze parallel execution.

\subsection{Program Instrumentation}
Program instrumentation involves recording runtime events to analyze the behavior of a program during its execution. By leveraging LLVM's \cite{llvm2004} instrumentation capabilities, we systematically track every access to persistent memory (PM), including reads, writes, and explicit memory synchronization commands such as flush and fence instructions. This detailed tracking is essential for identifying potential concurrency issues and ensuring data consistency.  Our approach incorporates two key LLVM tools: ThreadSanitizer (TSan) and DataFlowSanitizer (DFSan), each serving a specific purpose in our analysis.

\myparagraph{ThreadSanitizer (TSan)}
LLVM's TSan \cite{tsandoc}, originally developed by Google \cite{tsan2009} and now maintained by The Clang Team, is a tool that detects and reports data races through program instrumentation. TSan utilizes vector clocks to monitor thread interactions, including thread creations, lock acquisitions, and atomic operations such as compare-and-swap, fetch-and-add, etc. By capturing these interactions, TSan effectively establishes a comprehensive happens-before partial-ordering of program execution. 

We leverage TSan's vector clock updates to record the happens-before relationships among concurrent program events. This information is crucial for constructing the happens-before graph (\HBGName), which maps out the temporal and causal relationships between events, aiding in the detection of \NameRace conditions.

\myparagraph{DataFlowSanitizer (DFSan)}
LLVM's DFSan \cite{dfsan2020} is a dynamic data flow analysis tool capable of tagging memory locations and tracing their flow throughout the execution of the program. DFSan assigns labels to memory locations during read operations, which allows us to track how data propagates through the program.

We employ DFSan's memory tagging mechanism to label read operations and subsequently track all such tagged reads that influence write operations later in the program within each thread. These labels help us identify data dependencies by showing how data read at one point in the program affects subsequent write operations.
This capability enables us to understand which write operations to PM are influnced by a read operation from a different memory location in PM.

Currently, DFSan is limited to producing data-dependency analyses and does not account for control dependencies. This limitation means that we won't be able to detect all program dependence relationships and might miss some {\NameRace}s in our detection. Expanding our analysis to include control dependencies could allow for the identification of additional race conditions currently overlooked.

\subsection{Causal State Vector Clocks}
\label{sec:vc}

The vector clocks concept is used in many ways thought this work. Firstly, they are used by ThreadSanitizer \cite{tsan2009} to determine the happens-before relations in the program's execution. Secondly, use the same concept in our \HBGName analysis to determine different states of persistency and ordering of events in the program execution trace.

In our analysis we define vector clocks for each event node in the execution.
We use several types of vector clocks in order to keep track of different states during the execution trace. In general, each vector clock that we define is a $\Threads$ sized vector of event IDs (used like logical clocks) where each index $\Thread$ indicates a some known state from thread $\Thread$.

\myparagraph{\NameHAVC (\SignHAVC)}
Defined for each node $\NodeV \in \Nodes$ as the following function:
$$\HAVC{\NodeV}{\Thread}: \HAVCDef$$

An event $\NodeU$ is considered to \textit{happen-after} another event $\NodeV$ if $\HAVC{\NodeV}{\thread{\NodeU}} \leq \idx{\NodeU}$, establishing a causal order between these events.

\myparagraph{\NameHBVC (\SignHBVC)}
Defined for each node $\NodeV \in \Nodes$ as the following function:
$$\HBVC{\NodeV}{\Thread,\VarX}: \HBVCDef$$
This function determines the index of the latest event in thread $\Thread$ that precedes $\NodeV$ in $\HBG$ and affects the cache line associated with $\VarX$.
An event $\NodeU$ is considered to \textit{happen-before} another event $\NodeV$ if $\idx{\NodeU} \leq \HBVC{\NodeV}{\thread{\NodeU},\var{\NodeU}}$, establishing a causal order between these events.

\myparagraph{\NamePBVC (\SignPBVC)}
Defined for each node $\NodeV \in \Nodes$ as the following function:
$$\PBVC{\NodeV}{\Thread,\VarX}: \PBVCDef$$
This function determines the index of the latest event in thread $\Thread$ that precedes $\NodeV$ in $\HBG$, affects the cache line associated with $\VarX$, and ensures that $\VarX$ has been persisted.
An event $\NodeU$ is considered \textit{persisted-before} another event $\NodeV$ if $\idx{\NodeU} \leq \PBVC{\NodeV}{\thread{\NodeU},\var{\NodeU}}$.
Persistency here implies that there is a path in the $\HBG$ from $\NodeU$ to $\NodeV$ that contains a Flush event on the cache line associated with $\VarX$.

\subsection{\NameRace}

A \NameRace occurs when a write operation to persistent memory (PM) is influenced by a prior read operation from a non-persisted area of PM located on a different cache line.
This scenario risks compromising the integrity of the PM state if the write operation becomes durable before the read areas are persisted.
% , and such discrepancies are not corrected during the program recovery process.
Below, we formalize the definition of \NameRace based on our causal state vector clocks introduced in \autoref{sec:vc}.

\begin{definition}[\NameRace]
    \label{def:race}
    % Option 1
    % A \NameRace $( \NodeR, \NodeW, \NodeWEx ) \in \ReadNodes \times \WriteNodes \times \WriteNodes$ occurs if all the following are satisfied:
    % $$
    % \begin{aligned}
    %     & \var{\NodeR} = \var{\NodeW} \neq \var{\NodeWEx} \\
    %     & \thread{\NodeR} = \thread{\NodeWEx} \\
    %     & \NodeWEx \text{ is program-dependent on } \NodeR \\
    %     & \PBVC{\NodeWEx}{\thread{\NodeR}, \VarX} < \idx{\NodeR} \\
    %     & \PBVC{\NodeWEx}{\thread{\NodeW}, \VarX} < \idx{\NodeW} < \HAVC{\NodeR}{\thread{\NodeW}}
    % \end{aligned}
    % $$
    
    % Option 2
    % A \NameRace is defined to occur between a read node $\NodeR \in \ReadNodes$ and a write node $\NodeW \in \WriteNodes$ if both nodes access overlapping memory locations denoted as $\VarX$. Additionally, there exists another write node $\NodeWEx \in \WriteNodes$ that is program-dependent on $\NodeR$, operates on a different cache line, and satisfies the
    % % vector clock % I don't want a new line in the middle of the constraint
    % constraints $$\PBVC{\NodeWEx}{\thread{\NodeR}, \VarX} < \idx{\NodeR}$$ and $$\PBVC{\NodeWEx}{\thread{\NodeW}, \VarX} < \idx{\NodeW} < \HAVC{\NodeR}{\thread{\NodeW}}$$.

    % Option 3
    % A \NameRace is defined to occur between a read node $\NodeR \in \ReadNodes$ a write node $\NodeW \in \WriteNodes$ and a program-dependent $\NodeWEx \in \WriteNodes$ such that $(\NodeWEx, \NodeR) \in \PDEdges$, if both $\NodeR$ and $\NodeW$ access overlapping memory locations denoted as $\VarX$, and $\NodeWEx$ operates on a different cache line, and the following constrains are satisfied:
    % $$\PBVC{\NodeWEx}{\thread{\NodeR}, \VarX} < \idx{\NodeR}$$
    % $$\PBVC{\NodeWEx}{\thread{\NodeW}, \VarX} < \idx{\NodeW} < \HAVC{\NodeR}{\thread{\NodeW}}$$

    % Option 4
    A \NameRace is identified between a read node $\NodeR \in \ReadNodes$, a write node $\NodeW \in \WriteNodes$, and a program-dependent write node $\NodeWEx \in \WriteNodes$ where $(\NodeWEx, \NodeR) \in \PDEdges$.
    
    For this race to occur, both $\NodeR$ and $\NodeW$ must access the same memory location denoted as $\VarX$, while $\NodeWEx$ must operate on a different cache line.
    Additionally, the following two constraints are satisfied:
    \begin{gather*}
        \PBVC{\NodeWEx}{\thread{\NodeR}, \VarX} < \idx{\NodeR}\\
        \PBVC{\NodeWEx}{\thread{\NodeW}, \VarX} < \idx{\NodeW} < \HAVC{\NodeR}{\thread{\NodeW}}
    \end{gather*}

\end{definition}

The first vector clock constraint asserts that $\NodeR$ must not be persisted before $\NodeWEx$. If $\NodeR$ persisted before $\NodeWEx$, then there would be no race; the memory location that influences $\NodeWEx$ would already be in a stable persisted state, negating the possibility of a \NameRace.

The second vector clock constraint ensures that $\NodeW$ does not persist before $\NodeWEx$ and that it does not execute after $\NodeR$. This condition implies that $\NodeW$ occurs before $\NodeR$ or concurrently with it, allowing $\NodeW$ to potentially influence the value read by $\NodeR$ in certain executions of the program.

\section{Algorithm}
\label{sec:algorithm}
This section presents the algorithm designed to detect {\NameRace}s. The algorithm is comprised of three main stages: Initially, as detailed in \ref{sec:havc}, we construct the \NameHAVC ($\HAVC{}{}$) for each node. Subsequently, in \ref{sec:pbvc}, we develop the \NamePBVC ($\PBVC{}{}$) for each node. Lastly, in \ref{sec:cprd}, we employ these vector clocks to systematically identify {\NameRace}s throughout the program events.

After presenting the algorithm we will show some optimizations, correctness, and runtime complexity.

% This section describes the algorithm used to detect {\NameRace}s. The algorithm is comprised of three main stages: in \ref{sec:havc} we construct the $\HAVC{}{}$ for each node, in \ref{sec:pbvc} we construct $\PBVC{}{}$ for each node, and in \ref{sec:cprd}, we identify {\NameRace}s based on the two functions.

% ---------------------------------------------------------

\subsection{{\NameHAVC}s Builder}
\label{sec:havc}
In \autoref{alg:havc}, we perform a post-order traversal of all nodes in the \HBGName ($\HBG$). This traversal order ensures that each node $\NodeV$ is processed only after all nodes that happen-after it—its descendants—are processed.

During this traversal, the vector clock of each node, $\havc{\NodeV}{}$, is updated to the component-wise minimum of its descendants'
% children's?
vector clocks. This update process ensures that the vector clock $\havc{\NodeV}{}$ precisely reflects the \NameHAVC $\HAVC{\NodeV}{}$ for $\NodeV$ by the time its processing is complete, capturing the earliest interaction times dictated by the causal relationships within the $\HBG$.

% TODO: Should we add this?
\IfShowRuntimeComplexity
The runtime complexity of \autoref{alg:havc} is $\bigO{\abs{\Nodes}\abs{\Threads}^2}$.
In practice, the number of threads ($\abs{\Threads}$) in the execution will be much smaller than the number of event nodes $\abs{\Nodes}$, so we can say that the runtime complexity is closer to $\bigO{\abs{\Nodes}}$.
\fi

\begin{algorithm}
    \caption{{\NameHAVC}s Builder}
    \label{alg:havc}
    \Fn{\FHAVC{$\HBG$}}{
        \BlankLine
        Initialize $\havc{\NodeV}{\Thread} \gets +\infty$ \hfill $\forall \NodeV \in \Nodes, \Thread \in \Threads$
        \BlankLine
        \ForEach{node $\NodeV$ in $\HBG$ in post-order}{
            \label{alg:havc:mainloop}
            $\havc{\NodeV}{\thread{\NodeV}} \gets \idx{\NodeV}$ \label{alg:havc:initialize} \;
            \BlankLine
            \ForEach{child node $\NodeChild \such (\NodeV, \NodeChild) \in \HBEdges$}{
                \label{alg:havc:childloop}
                \ForEach{$\Thread \in \Threads$}{
                    $\havc{\NodeV}{\Thread} \gets \Min{\havc{\NodeV}{\Thread}}{\havc{\NodeChild}{\Thread}}$ \label{alg:havc:update} \;
                }
            }
        }
        \BlankLine
        % \KwRet $\havc{\NodeV}{} \hfill \forall \NodeV \in \Nodes$\;
        \KwRet $\havc{}{}$\;
    } 
\end{algorithm}

% Algorithm - 2. PBVC
% ---------------------------------------------------------
\subsection{{\NamePBVC}s Builder}
\label{sec:pbvc}
In \autoref{alg:pbvc}, we perform a reversed post-order traversal of all nodes in the \HBGName ($\HBG$). This traversal order ensures that each node $\NodeV$ is processed only after all nodes that happen-before it—its ancestors—have been visited.

During the traversal, we update two vector clocks for each node $\NodeV$: the \NameHBVC ($\hbvc{\NodeV}{}$) and the \NamePBVC ($\pbvc{\NodeV}{}$). Each vector clock is updated to the component-wise maximum of the vector clocks of its ancestors to ensure it captures the most comprehensive interaction history. Specifically, if $\NodeV$ is a flush node, $\pbvc{\NodeV}{}$ is updated to match $\hbvc{\NodeV}{}$, signaling that all interactions up to this flush are now considered persisted.

We maintain a separate vector clock for each variable to accurately track and reflect the effects of flush events on corresponding variables (practically, on the relevant cache lines).

\IfShowRuntimeComplexity
The runtime complexity of \autoref{alg:pbvc} is $\bigO{\abs{\Nodes}\abs{\Vars}\abs{\Threads}^2}$. And since $\abs{T} << \abs{\Nodes}$ and $\abs{\Vars} < \abs{\Nodes}$, we can say that the runtime complexity is closer to $\bigO{\abs{\Nodes}^2}$.
\fi

\begin{algorithm}
    \caption{{\NamePBVC}s Builder}
    \label{alg:pbvc}
    \Fn{\FPBVC{$\HBG$}}{
        
        \BlankLine
        
        $\hbvc{\NodeV}{\Thread, \VarX} \gets -\infty$ \hfill $\forall \NodeV \in \Nodes, \Thread \in \Threads, \VarX \in \Vars$
        
        $\pbvc{\NodeV}{\Thread, \VarX} \gets -\infty$ \hfill $\forall \NodeV \in \Nodes, \Thread \in \Threads, \VarX \in \Vars$
        
        \BlankLine
        
        \ForEach{node $\NodeV$ in $\HBG$ in reversed post-order}{
            $\hbvc{\NodeV}{\thread{\NodeV},\var{\NodeV}} \gets \idx{\NodeV}$
        
            \BlankLine
            
            % Take from parents
            % \Comment*[l]{Learn from parent nodes}
            \ForEach{parent node $\NodeParent$ \such $(\NodeParent, \NodeV) \in \HBEdges$}{
                \ForEach{$\Thread \in \Threads$}{
                    \ForEach{$\VarY \in {\Vars}$}{
                        $\hbvc{\NodeV}{\Thread,\VarY} \gets \max \left( \hbvc{\NodeV}{\Thread,\VarY}, \hbvc{\NodeParent}{\Thread,\VarY} \right)$
                        
                        $\pbvc{\NodeV}{\Thread,\VarY} \gets \max \left( \pbvc{\NodeV}{\Thread,\VarY}, \pbvc{\NodeParent}{\Thread,\VarY} \right)$
                    }
                }
            }
        
            \BlankLine
            
            % F
            % \Comment*[l]{Handle Flush nodes}
            \If{$\NodeV \in \FlushNodes$}{
                \ForEach{$\Thread \in \Threads$}{
                    $\pbvc{\NodeV}{\Thread,\var{\NodeV}} \gets \hbvc{\NodeV}{\Thread,\var{\NodeV}}$
                }
            }
        }
        \BlankLine
        % \KwRet $\pbvc{\NodeV}{} \hfill \forall \NodeV \in \Nodes$\;
        \KwRet $\pbvc{}{}$
    }
\end{algorithm}

\subsection{Algorithmic Optimizations}

This section discusses several key optimizations implemented to enhance both the performance and efficiency of the algorithm.

\myparagraph{Intra-Thread Cache Line Linked Lists}
We implement linked lists within each thread for event nodes that affect the same cache line. This allows for rapid iteration over potential write nodes within the critical window defined by $\PBVC{}{}$ and $\HAVC{}{}$, significantly reducing the runtime complexity of \autoref{alg:cprd}.
% towards $\bigO{\abs{\races}}$

% \myparagraph{Integrated Node Processing}
\myparagraph{Iterations Coalescing}
Instead of separately executing the two final algorithms, we consolidate their operations into a single pass over all nodes. Once a node $\NodeV$ is processed we can immediately determine $\HAVC{\NodeV}{}$ and $\PBVC{\NodeV}{}$ and therefor look for the bugs defined by their range. This integration reduces memory overhead by eliminating the need to store $\pbvc{}{}$ for each node.
% We consolidate the operations of the final two algorithms into a single traversal over all nodes. This integration allows for immediate access to $\HAVC{\NodeV}{}$ and $\PBVC{\NodeV}{}$ upon processing each node $\NodeV$, thus eliminating the need to store $\pbvc{}{}$ for each node separately. This approach not only reduces memory overhead but also simplifies the computational workflow.


\myparagraph{Per-Thread Vector Clock Management}
Instead of maintaining separate vector clocks $\hbvc{\NodeV}{\Thread, \VarX}$ and $\pbvc{\NodeV}{\Thread, \VarX}$ for every node across all variables and threads, we manage vector clocks on a per-thread basis. We propagate updates through partial vector clocks linked to each node, reducing memory usage and enhancing processing speed by avoiding redundant duplication of vector clocks within threads.
% Rather than maintaining a $\hbvc{\NodeV}{\Thread, \VarX}$ and $\pbvc{\NodeV}{\Thread, \VarX}$ for every node across all variables and threads, we maintain thread-specific vector clocks and propagate updates via partial vector clocks associated with each node. This adjustment not only conserves memory but also enhances processing speed by minimizing redundant vector clocks duplication between nodes of the same thread.

% \myparagraph{Dirty Variables Vector Clock (DVVC) Strategy}
\myparagraph{Dirty Variables Vector Clock (DVVC)}
To tackle the performance degradation associated with propagation of vector clocks for all variables, we employ a mechanism we call DVVC. This strategy focuses updates only on variables that necessitate changes, utilizing a flagging system to manage updates across threads. When a variable $\VarX$ in one thread is updated, a DVVC flags this event, ensuring that other threads are notified only as necessary. This method significantly reduces the runtime of the algorithm.

\section{Related Work}
\label{sec:relatedwork}
The evolution of Persistent Memory (PM) technologies has catalyzed the development of numerous tools designed to detect and mitigate consistency issues in concurrent PM programs. This surge in tool creation reflects the complex challenges posed by PM's unique characteristics, such as byte-addressability and durability, which complicate traditional programming models especially in multi-threaded environments.

Among the notable contributions is PMRace, introduced by Chen, Zhangyu, et al. \cite{pmrace2022}, which marks a significant advancement in bug detection for concurrent NVM programs. Unlike earlier approaches that did not extensively address concurrency, PMRace employs a fuzzing-based technique to uncover inter-thread inconsistencies and synchronization issues. The tool identifies and tests PM alias pairs—pairs of read/write operations to the same PM address—to simulate delays that might expose potential inconsistencies.

Witcher, introduced by Fu, Xinwei, et al. \cite{witcher2021}, further explores the state space of NVM, utilizing an LLVM pass to trace program execution and detect violations of NVM state. This tool emphasizes crash consistency by testing the persistence order of operations through crash simulations, aiming for scalability and precision without the need for manual source code annotations.

Another important tool is XFDetector \cite{xfdetector2020}, which focuses on detecting 'Cross-Failure Bugs'—bugs that manifest due to discrepancies between pre-failure and post-failure states. These include both cross-failure races, where a post-failure operation relies on unpersisted data, and semantic bugs, where operations post-recovery misuse data that, while persisted, is deemed invalid by program semantics.

PMTest \cite{pmtest2019} provides a more granular approach by offering low-level checkers like isPersist and isOrderedBefore, which allow developers to assert specific program invariants and directly check the persistence states of memory locations, thus aiding in the identification of inconsistency bugs.

These tools collectively highlight the diverse strategies employed to tackle the intricate issues of PM programming, from dynamic analysis to program instrumentation and beyond.
% However, each comes with limitations in either scope or applicability, particularly in handling the intricate interplays of multi-threaded operations in PM environments. Our work with \SignRaceDetector builds on these foundations, aiming to provide a comprehensive solution that addresses the gaps left by existing tools in detecting and resolving \NameRace conditions effectively.
