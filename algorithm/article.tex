\begin{abstract}

The introduction of new NVM technologies with byte addressable access and DRAM performance has increased interest in developing crash-consistent software.
This type of software introduces a new type of inconsistency bugs between the volatile CPU cache and the persistent NVM state.

This research introduces \SignRaceDetector, a concurrent NVM bug detector that analyzes the program trace using a graph search algorithm.

\end{abstract}

Nonvolatile memory (NVM) technologies, such as Intel’s Optane DC Persistent Memory \cite{intel2019optane}, offer both persistence similar to disks with performance close to that of DRAM. NVM storage is accessed, like DRAM, with load and store instructions. This provides new opportunities to design crash-consistent software without high storage overhead. However, designing and implementing such programs is difficult. NVM data on a volatile cache may not persist after a crash, and it may also evict cache lines in an arbitrary order, which may differ from the program’s store order.

To ensure consistency of NVM state, developers need to explicitly evict cache lines to the NVM. This can be done with explicit flush (e.g., CLWB) and fence (e.g., SFENCE) instructions \cite{intel2020abi}. Due to the need to ensure correct cache line evictions, even experienced programmers may introduce inconsistency bugs, if they are not experienced with PM programming practices. This introduces a need for special bug detectors that could help developers find such complicated bugs. Previous bug detectors, aimed at detecting data inconsistencies, won’t necessarily be able to find NVM related bugs. This type of programming model that uses byte addressable persistent memory did not exist before. 

In this work, we focus on a specific type of bug that can be introduced in concurrent NVM programs. Previously coined as \NamePMRaceRace \cite{pmrace2022}, a bug that occurs when an NVM location affects data written to another NVM location before being persisted. Such bug can cause an inconsistent NVM state after a crash if the affected written address got persisted before the read address. In the following, we refer to this bug as \textbf{\race}.

Previous work \cite{pmrace2022} attempted to detect the bug using a smart fuzzing technique to explore the inter-thread interleaving of the program.
We attempt to solve the interleaving exploration using a vector clock analysis that detects happens-before relations between program events \cite{lamport1978}.
To do this, we use LLVM's ThreadSanitizer \cite{tsan2009}.
In addition, we want to detect all write events to persistent memory that are affected by a read event from persistent memory. We will use data-flow analysis to determine whether a read event affects a write event later in the execution.
For this, we will use LLVM's DataFlowSanitizer \cite{dfsan2020}.

Using both the happens-before analysis and the data-flow analysis we can construct 2 graphs that represent the relations between all execution events.
A \HBGName, denoted as $\HBG$, and a \PDGName \cite{pd1991} denoted as $\PDG$
\NameRaceDetector will use the 2 graphs to traverse the program execution trace and report all discovered bugs using the algorithm presented later in \autoref{sec:algorithm}.

\subsection{Program Instrumentation}
Program instrumentation involves recording runtime events to analyze the behavior of a program during its execution. By leveraging LLVM's Intermediate Representation (IR) for instrumentation, we systematically track every access to persistent memory (PM), including reads, writes, and explicit memory synchronization commands such as flush and fence instructions. Additionally, we utilize LLVM's ThreadSanitizer \cite{tsan2009}, originally used for identifying potential data races, for capturing happens-before relations, and LLVM's DataFlowSanitizer \cite{dfsan2020} for identifying program dependency relations among execution events at runtime.


\myparagraph{Happens-Before Analysis}
LLVM's ThreadSanitizer \linebreak (TSan), originally developed by Google \cite{tsan2009} and now maintained by The Clang Team \cite{tsandoc}, is a tool that detects and reports data races through program instrumentation. TSan utilizes vector clocks to monitor thread interactions including thread creations, lock acquisitions, and atomic operations such as compare-and-swap, fetch-and-add, etc. This process effectively establishes a comprehensive happens-before partial-ordering of program execution. 

We leverage the vector clock updates mechanism of TSan to record the happens-before relationships among concurrent program events.

\subsection{Program Trace Representation}
The program trace categorizes events into three main types: event nodes $\Nodes$, happens-before edges $\HBEdges$, and program dependency edges $\PDEdges$. We denote the subsets of Read, Write, and Flush event nodes as $\ReadNodes$, $\WriteNodes$, and $\FlushNodes$, respectively. Each event node $\NodeV$ is associated with a variable $\var{\NodeV} \in \Vars$ indicating the memory address accessed, and a thread $\thread{\NodeV} \in \Threads$ indicating the executing thread. Each event node is also sequentially identified by $\idx{\NodeV} \in \IDs$ within its thread, reflecting the execution order.

Lamport’s happens-before graph (HBG) \cite{lamport1978} is a theoretical construct used to model the execution dynamics of concurrent programs. Within this graph, every executed instruction is represented as a node, and directed edges between these nodes create a partial-order that outlines the execution order between instructions.
This abstraction is particularly useful for analyzing concurrent executions \cite{chess2008}, as it decouples the execution order from the actual timing of instructions. Consequently, different executions that may run at varying speeds but share the same happens-before graph are considered behaviorally equivalent, reflecting consistent execution behavior despite temporal differences.
% Previous works have also modeled program execution in this way \cite{chess2008}.

We abstract the program execution with a happens-before graph and denote it as $\HBG = (\Nodes, \HBEdges)$. A directed path from node $\NodeE_1$ to node $\NodeE_2$ implies that the event at $\NodeE_1$ happens-before the event at $\NodeE_2$, establishing a precedence relation.
The graph structures the nodes to reflect the execution of the program threads. Nodes within the same thread are linked by intra-thread edges, illustrating sequential execution steps, while nodes across different threads are linked by inter-thread edges, demonstrating the happens-before relationship between them.

The Dynamic Dependency Graph (DDG) \cite{pd1988} is a directed, acyclic graph that models the execution flow of a program as a partial order. In the DDG, each node corresponds to an executed instruction, and directed edges illustrate the dependencies that exist between these instructions.
Dependencies in a DDG can be classified into several types \cite{pd1992}, primarily including data dependencies and control dependencies. A data dependency arises between two operations when the output of one operation (e.g., a value produced) is required as input for the other operation. Conversely, a control dependency exists when the execution path of one operation depends on the outcome of a conditional branch affecting another operation.

We denote the DDG by $\PDG = (\Nodes, \PDEdges)$. Within this graph, an edge from $\tempNodeOne$ to $\tempNodeTwo$ indicates that the execution of $\tempNodeOne$ relies on the result of $\tempNodeTwo$.

\subsection{State Vector Clocks}
Vector clocks, based on Lamport's timestamps \cite{lamport1978} and further developed in \cite{fidge1987vc} and \cite{mattern1988vc}, are a widely used method to capture the causality between events in parallel and distributed systems, and to determine the happens-before partial-order between them. Intuitively, vector clocks represent the known state of execution across all program threads, from the view of a single event in the execution.
% Vector clocks, building upon Lamport's timestamps \cite{lamport1978} and further developed in \cite{fidge1987vc} and \cite{mattern1988vc}, are a widely used mechanism for capturing causality among events in parallel and distributed systems. 
% This tool is used to determine the happens-before partial-order of the executed program events. Intuitively, vector clocks represent the known state of execution across all program threads, from the view of a single event in the execution.


We use vector clocks in many ways thought this work. Firstly, they are used by ThreadSanitizer \cite{tsan2009} to determine the happens-before relations in the program's execution. Secondly, use the same concept in our \HBGName analysis to determine different states of persistency and ordering of events in the program execution trace.

In our analysis we define vector clocks for each event node in the execution.
We use several types of vector clocks in order to keep track of different states during the execution trace. In general, each vector clock that we define is a $\Threads$ sized vector of event IDs (used like logical clocks) where each index $\Thread$ indicates a some known state from thread $\Thread$.

\myparagraph{\NameHAVC (\SignHAVC)}
Defined for each node $\NodeV \in \Nodes$ as the following function:
$$\HAVC{\NodeV}{\Thread}: \HAVCDef$$
This function determines the index of the earliest event in thread $\Thread$ that happens-after $\NodeV$ in $\HBG$.
An event $\NodeU$ is considered to \textit{happen-after} another event $\NodeV$ if $\HAVC{\NodeV}{\thread{\NodeU}} \leq \idx{\NodeU}$, establishing a causal order between these events.

\myparagraph{\NameHBVC (\SignHBVC)}
Defined for each node $\NodeV \in \Nodes$ as the following function:
$$\HBVC{\NodeV}{\Thread,\VarX}: \HBVCDef$$
This function determines the index of the latest event in thread $\Thread$ that precedes $\NodeV$ in $\HBG$ and affects the cache line associated with $\VarX$.
An event $\NodeU$ is considered to \textit{happen-before} another event $\NodeV$ if $\idx{\NodeU} \leq \HBVC{\NodeV}{\thread{\NodeU},\var{\NodeU}}$, establishing a causal order between these events.

\myparagraph{\NamePBVC (\SignPBVC)}
Defined for each node $\NodeV \in \Nodes$ as the following function:
$$\PBVC{\NodeV}{\Thread,\VarX}: \PBVCDef$$
This function determines the index of the latest event in thread $\Thread$ that precedes $\NodeV$ in $\HBG$, affects the cache line associated with $\VarX$, and ensures that $\VarX$ has been persisted.
An event $\NodeU$ is considered \textit{persisted-before} another event $\NodeV$ if $\idx{\NodeU} \leq \PBVC{\NodeV}{\thread{\NodeU},\var{\NodeU}}$.
Persistency here implies that there is a path in the $\HBG$ from $\NodeU$ to $\NodeV$ that contains a Flush event on the cache line associated with $\VarX$.

\section{Algorithm}
\label{sec:algorithm}
This section presents the algorithm designed to detect {\NameRace}s. The algorithm is comprised of three main stages: Initially, as detailed in \ref{sec:havc}, we construct the \NameHAVC ($\HAVC{}{}$) for each node. Subsequently, in \ref{sec:pbvc}, we develop the \NamePBVC ($\PBVC{}{}$) for each node. Lastly, in \ref{sec:cprd}, we employ these vector clocks to systematically identify {\NameRace}s throughout the program events.

After presenting the algorithm we will show some optimizations, correctness, and runtime complexity.

The algorithm is comprised of three main stages: in \ref{sec:havc} we construct the $\HAVC{}{}$ for each node, in \ref{sec:pbvc} we construct $\PBVC{}{}$ for each node, and in \ref{sec:cprd}, we identify {\NameRace}s based on the two functions.

\subsection{{\NameHAVC}s Builder}
\label{sec:havc}
In \autoref{alg:havc}, we perform a post-order traversal of all nodes in the \HBGName ($\HBG$). This traversal order ensures that each node $\NodeV$ is processed only after all nodes that happen-after it—its descendants—are processed.

During this traversal, the vector clock of each node, $\havc{\NodeV}{}$, is updated to the component-wise minimum of its descendants'
% children's?
vector clocks. This update process ensures that the vector clock $\havc{\NodeV}{}$ precisely reflects the \NameHAVC $\HAVC{\NodeV}{}$ for $\NodeV$ by the time its processing is complete, capturing the earliest interaction times dictated by the causal relationships within the $\HBG$.

\begin{algorithm}
    \caption{{\NameHAVC}s Builder}
    \label{alg:havc}
    \Fn{\FHAVC{$\HBG$}}{
        \BlankLine
        Initialize $\havc{\NodeV}{\Thread} \gets +\infty$ \hfill $\forall \NodeV \in \Nodes, \Thread \in \Threads$ \;
        \BlankLine
        \ForEach{node $\NodeV$ in $\HBG$ in post-order}{
            \label{alg:havc:mainloop}
            $\havc{\NodeV}{\thread{\NodeV}} \gets \idx{\NodeV}$ \label{alg:havc:initialize} \;
            \BlankLine
            \ForEach{child node $\NodeChild \such (\NodeV, \NodeChild) \in \HBEdges$}{
                \label{alg:havc:childloop}
                \ForEach{$\Thread \in \Threads$}{
                    $\havc{\NodeV}{\Thread} \gets \Min{\havc{\NodeV}{\Thread}}{\havc{\NodeChild}{\Thread}}$ \label{alg:havc:update} \;
                }
            }
        }
        \BlankLine
        % \KwRet $\havc{\NodeV}{} \hfill \forall \NodeV \in \Nodes$\;
        \KwRet $\havc{}{}$\;
    } 
\end{algorithm}

\subsection{{\NamePBVC}s Builder}
\label{sec:pbvc}
In \autoref{alg:pbvc}, we perform a reversed post-order traversal of all nodes in the \HBGName ($\HBG$). This traversal order ensures that each node $\NodeV$ is processed only after all nodes that happen-before it—its ancestors—have been visited.

During the traversal, we update two vector clocks for each node $\NodeV$: the \NameHBVC ($\hbvc{\NodeV}{}$) and the \NamePBVC ($\pbvc{\NodeV}{}$). Each vector clock is updated to the component-wise maximum of the vector clocks of its ancestors to ensure it captures the most comprehensive interaction history. Specifically, if $\NodeV$ is a flush node, $\pbvc{\NodeV}{}$ is updated to match $\hbvc{\NodeV}{}$, signaling that all interactions up to this flush are now considered persisted.

We maintain a separate vector clock for each variable to accurately track and reflect the effects of flush events on corresponding variables (practically, on the relevant cache lines).

\begin{algorithm}
    \caption{{\NamePBVC}s Builder}
    \label{alg:pbvc}
    \Fn{\FPBVC{$\HBG$}}{
        \BlankLine
        Initialize $\hbvc{\NodeV}{\Thread, \VarX} \gets -\infty$ \hfill $\forall \NodeV \in \Nodes, \Thread \in \Threads, \VarX \in \Vars$ \;
        Initialize $\pbvc{\NodeV}{\Thread, \VarX} \gets -\infty$ \hfill $\forall \NodeV \in \Nodes, \Thread \in \Threads, \VarX \in \Vars$ \;
        \BlankLine
        \ForEach{node $\NodeV$ in $\HBG$ in reversed post-order}{
            $\hbvc{\NodeV}{\thread{\NodeV},\var{\NodeV}} \gets \idx{\NodeV}$\;
        
            \BlankLine
            
            % Take from parents
            % \Comment*[l]{Learn from parent nodes}
            \ForEach{parent node $\NodeParent$ \such $(\NodeParent, \NodeV) \in \HBEdges$}{
                \ForEach{$\Thread \in \Threads$}{
                    \ForEach{$\VarY \in {\Vars}$}{
                        $\hbvc{\NodeV}{\Thread,\VarY} \gets \max \left( \hbvc{\NodeV}{\Thread,\VarY}, \hbvc{\NodeParent}{\Thread,\VarY} \right)$\;
                        $\pbvc{\NodeV}{\Thread,\VarY} \gets \max \left( \pbvc{\NodeV}{\Thread,\VarY}, \pbvc{\NodeParent}{\Thread,\VarY} \right)$\;
                    }
                }
            }
        
            \BlankLine
            
            % F
            % \Comment*[l]{Handle Flush nodes}
            \If{$\NodeV \in \FlushNodes$}{
                \ForEach{$\Thread \in \Threads$}{
                    $\pbvc{\NodeV}{\Thread,\var{\NodeV}} \gets \hbvc{\NodeV}{\Thread,\var{\NodeV}}$\;
                }
            }

\textbf{Persistent Memory Bugs Detectors:}
Like PMRACE \cite{pmrace2022}, which focuses on finding concurrent bugs. 
Others like Yashme \cite{yashme2022}, Witcher \cite{witcher2021}, PMDebugger \cite{pmdebugger2021}, XFDetector \cite{xfdetector2020}, PMTest \cite{pmtest2019}















The concept of operating systems for coffee machines is not entirely novel. Previous attempts have focused on various aspects of coffee preparation and automation. Here, we provide a brief overview of these endeavors and highlight how ESPLOS improves upon them.



\textbf{PMRace} \cite{pmrace2022} – a NVM bug detector designed for concurrent NVM programs.
Until recently, most works didn’t focus on NVM bugs in concurrent programs, mostly due to the complex search space that thread scheduling introduces.
In ASPLOS 2022, Chen, Zhangyu, et al. introduced PMRace, that focuses on bug detection in concurrent NVM programs. 
PMRace is a fuzzing-based bug detector that is aimed at detecting 2 types of PM bugs:
\begin{itemize}
    \item PM inter-thread inconsistencies – a program execution in which one thread makes durable side effects based on non-persisted data written by another thread. This is the definition of our concurrent persistency race.
    \item PM synchronization inconsistencies - an inconsistency between a persistent synchronization variable (e.g., a lock, a mutex, etc.) and the non-persistent thread state.
\end{itemize}
PMRace detects PM inter-thread inconsistencies by finding all pairs of read/write operations to the same PM addresses (named PM alias pairs). It later simulates a delay after the write operation that allows the read operation to continue and to hopefully introduce the inconsistency bug.

PMRace tries to maximize its coverage of PM alias pairs to detect more bugs. To find the inconsistencies, PMRace detects program dependency relations and sees if an NVM location, that is dependent on the PM alias pair’s data, is modified with un-persisted data.

\paragraph{Witcher} \cite{witcher2021} – a crash consistency bug detector for NVM software that focuses on exploring the NVM state space.
Witcher uses an LLVM pass to trace the program's execution and to detect possible violations of NVM state. It finds likely invariants on the program’s persistence order and tests its correctness by simulating a crash. Later it checks the equivalence of the NVM state with and without the simulated crash and finds NVM violations if the states are different.
Witcher is designed to be scalable (doesn’t suffer from test space explosion), automatic (doesn’t require manual source code annotations), and precise (doesn’t produce false positives).
Witcher doesn’t focus on exploring thread interleaving, and therefore isn’t suited to find difficult concurrency NVM bugs. They leave this for future work.

\paragraph{VSV-D} (Vector Space Verification – Durability) \cite{vsvd2021} – a dynamic analysis tool that checks durable linearizability at runtime.
Requires user annotations – granularity of operations is defined by the user.
Mostly verifies that all required NVM data is guaranteed to be flushed.

\paragraph{XFDetector} (Cross-Failure Detector) \cite{xfdetector2020}
Detects NVM bugs between the pre-failure and post-failure stages, named Cross-Failure Bugs.
These bugs can be categorized into 2 classes:
\begin{itemize}
    \item Cross-failure races – a post-failure operation that relies on data that wasn’t persisted in the pre-failure stage.
    \item Cross-failure semantic bugs – a post-failure operation that reads data that might be persistent but is considered invalid by program semantics.
\end{itemize}

\paragraph{PMTest} \cite{pmtest2019}
Supplies 2 low-level program checkers:
\begin{itemize}
\item isPersist – checks if an NVM memory location is persisted.
\item isOrderedBefore – checks if an NVM memory location is persisted before another location.
\end{itemize}

Using these checkers, the user can assert program invariants and detect inconsistency bugs.

\textbf{Recipe} \cite{recipe2019} an approach for converting concurrent DRAM data structures into crash consistent data structures for persistent memory.

The common conversion step is to insert a cache line flush and memory fence instructions after each store. 
This approach can produce a bug where data that is modified in one thread can be read by another thread before being persisted. This data can later be used to update other NVM locations that might get persisted before the original data persists. If a crash occurs before the original data persists but after the dependent data persists in another thread, an inconsistency bug will occur. The NVM state after the crash is no longer consistent.

In this work we call such bug a Concurrent Persistency Race, and this is the bug that we hope to detect with our bug detector.
