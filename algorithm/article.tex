\begin{abstract}

The introduction of new NVM technologies with byte addressable access and DRAM performance has increased interest in developing crash-consistent software.
This type of software introduces a new type of inconsistency bugs between the volatile CPU cache and the persistent NVM state.

This research introduces CPRD, a concurrent NVM bug detector that analyzes the program trace using a graph search algorithm.

\end{abstract}

Nonvolatile memory (NVM) technologies, such as Intel’s Optane DC Persistent Memory \cite{intel2019optane}, offer both persistence similar to disks with performance close to that of DRAM. NVM storage is accessed, like DRAM, with load and store instructions. This provides new opportunities to design crash-consistent software without high storage overhead. However, designing and implementing such programs is difficult. NVM data on a volatile cache may not persist after a crash, and it may also evict cache lines in an arbitrary order, which may differ from the program’s store order.

To ensure consistency of NVM state, developers need to explicitly evict cache lines to the NVM. This can be done with explicit flush (e.g., CLWB) and fence (e.g., SFENCE) instructions \cite{intel2020abi}. Due to the need to ensure correct cache line evictions, even experienced programmers may introduce inconsistency bugs, if they are not experienced with PM programming practices. This introduces a need for special bug detectors that could help developers find such complicated bugs. Previous bug detectors, aimed at detecting data inconsistencies, won’t necessarily be able to find NVM related bugs. This type of programming model that uses byte addressable persistent memory did not exist before. 

In this work, we focus on a specific type of bug that can be introduced in concurrent NVM programs. Previously coined as \pmracerace \cite{pmrace2022}, a bug that occurs when an NVM location affects data written to another NVM location before being persisted. Such bug can cause an inconsistent NVM state after a crash if the affected written address got persisted before the read address. In the following, we refer to this bug as \race.

Previous work \cite{pmrace2022} attempted to detect the bug using a smart fuzzing technique to explore the inter-thread interleaving of the program.
We attempt to solve the interleaving exploration using a vector clock analysis that detects happen-before relations between program events \cite{lamport1978}.
To do this, we use LLVM's ThreadSanitizer \cite{tsan2009}.
In addition, we want to detect all write events to persistent memory that are affected by a read event from persistent memory. We will use data-flow analysis to determine whether a read event affects a write event later in the execution.
For this, we will use LLVM's DataFlowSanitizer \cite{dfsan2020}.

Using both the happen-before analysis and the data-flow analysis we can construct 2 graphs that represent the relations between all execution events.
A \HBGName, denoted as $\HBG$, and a \PDGName \cite{dpdg1991} denoted as $\PDG$
\myrace detector will use the 2 graphs to traverse the program execution trace and report all discovered bugs using the algorithm presented later in \autoref{sec:algorithm}.

\myparagraph{Happen-Before Analysis}
LLVM's ThreadSanitizer \cite{tsan2009}, originally developed by Google, is a data race detection tool that instruments program execution and reports data races, using a vector clock analysis \cite{lamport1978}.
In Lamport's original paper, vector clocks are updated when a process sends a message to another process. In the case of ThreadSanitizer, the messages are considered to be any event in one thread that is guarantied to happen before another event in another thread.
Events like thread creation, join operations, lock acquisitions and releases, and use of atomic primitives like InterlockIncrement, InterlockXchg etc.

We utilize ThreadSanitizer's precise instrumentation and vector clock updates in order to record happen-before edges between program events.

\section{Algorithm}
\label{sec:algorithm}

In the following section we will present the algorithm used to detect {\cprd}s.
First we will define the \cprd formally and later present the algorithm of detecting it.

Events within the program trace are organized into three main categories: event nodes $\Nodes$, happens-before edges $\HBEdges$, and program dependency edges $\PDEdges$. Specifically, the subsets $\ReadNodes, \WriteNodes, \FlushNodes$ denote the \textbf{Read}, \textbf{Write}, and \textbf{Flush} nodes, highlighting the types of operations performed at each node.
For every event node $\NodeV$, we assign $\var{\NodeV} \in \Vars$ to indicate the variable (or memory address) that is being accessed, modified, or flushed. Additionally, $\thread{\NodeV} \in \Threads$ identifies the thread in which the event at node $\NodeV$ occurs.
Furthermore, each event in the trace is assigned a sequential ID, represented by $\idx{\NodeV}$. It's important to note that within each thread, this ID increments sequentially, reflecting the forward progression of program execution.
We denote \HBGName as $\HBG = (\Nodes, \HBEdges)$. We say that an event node $\NodeE_1$ happen-before $\NodeE_2$ if there is a path in $\HBG$ from $\NodeE_1$ to $\NodeE_2$.
% We denote \PDGName as $\PDG = (\Nodes, \PDEdges)$.

A \race emerges when a modification to persistent memory (PM) is influenced by a read operation from an area in PM that has not yet been persisted (and are located in different cache lines).
To detect such race, we assess the persistence status of the memory address $\VarX$ involved in the read operation at the time the corresponding PM modification is executed. 

$\VarX$ is considered persisted at the moment of the event node $\NodeWEx$ if it meets one of the following conditions: A Flush event precedes $\NodeWEx$ and occurs after the read event $\NodeR$ that influences it, or, for every write event to $\VarX$ not succeeding the read event $\NodeR$, there exists a Flush event that precedes $\NodeWEx$. This ensures that $\VarX$ is in a persisted state by the time $\NodeWEx$ takes place, having been flushed following the influencing read operation or write operations that might have affected the read.
% We say that $\VarX$ is persisted at the time of the event node $\NodeWEx$ if a Flush event happen-before $\NodeWEx$ and happen-after the influencing read event $\NodeR$ or after all write events to $\VarX$ that don't happen-after the read event $\NodeR$, there is a flush event that happen-before the $\NodeWEx$ event.

\begin{definition}
    \label{def:race}
    We define a \race between a read node $\NodeR \in \ReadNodes$ and a write node $\NodeW \in \WriteNodes$ if both operate on overlapping memory locations, $\NodeR$ does not happen-before $\NodeW$, and $\exists \NodeWEx \in \WriteNodes$ such that $\NodeWEx$ is program-dependent on $\NodeR$ (in the same thread and operates on a different cache line), and there is no flush event $\NodeF$ that happen-before $\NodeWEx$ such that $\NodeF$ happen-after $\NodeR$ or happen-after $\NodeW$.
\end{definition}

% In order to inquire about the persistency state of memory location $\VarX$ at any given point in the execution, we will define two functions for each event node $\NodeV \in \Nodes$: $\HBVC{\NodeV}{\Thread,\VarX}$, the last node's index in thread $\Thread$ of variable $\VarX$ that happen-before the node $\NodeV$, and $\PBVC{\NodeV}{\Thread,\VarX}$, the last node's index in thread $\Thread$ of variable $\VarX$ that was persisted before the node $\NodeV$, meaning that it  happen-before a flush event (on the same cache line).

% To evaluate the persistence status of memory location $\VarX$ at any point during execution, we introduce two functions for each event node $\NodeV \in \Nodes$. The function $\HBVC{\NodeV}{\Thread,\VarX}$ identifies the index of the last node in thread $\Thread$ concerning variable $\VarX$ that precedes node $\NodeV$. The function $\PBVC{\NodeV}{\Thread,\VarX}$ determines the index of the last node in thread $\Thread$ concerning variable $\VarX$ that was persisted prior to node $\NodeV$. This implies the node occurred before a flush event targeting the same cache line.
To evaluate the persistence status of memory location $\VarX$ at any point during execution, for each node we $\NodeV \in \Nodes$ introduce the function $\PBVC{\NodeV}{\Thread,\VarX}$ that determines the index of the last node in thread $\Thread$ concerning variable $\VarX$ that was persisted prior to node $\NodeV$. This implies the node occurred before a flush event targeting the same cache line.
In addition, for each event node we introduce the function, $\HAVC{\NodeV}{\Thread}$ which identifies the index of the first node in thread $\Thread$ that happen-after node $\NodeV$.

Using these functions, we will redefine \cprd as follows.
\begin{definition}
    \label{def:race2}
    We define a \race between a read node $\NodeR \in \ReadNodes$ and a write node $\NodeW \in \WriteNodes$ if both operate on overlapping memory locations, and $\exists \NodeWEx \in \WriteNodes$ such that $\NodeWEx$ is program-dependent on $\NodeR$ (in the same thread and operates on a different cache line), and 
    $$\PBVC{\NodeWEx}{\thread{\NodeW}, \var{\NodeW}} < \idx{\NodeW} < \HAVC{\NodeR}{\thread{\NodeW}}$$
    and
    $$\PBVC{\NodeWEx}{\thread{\NodeWEx}, \var{\NodeR}} < \idx{\NodeR}$$
\end{definition}

\subsection{Algorithm}
The algorithm is comprised of three main stages: in \autoref{alg:havc} we construct the $\HAVC{}{}$ for each node, in \autoref{alg:pbvc} we construct $\PBVC{}{}$ for each node, and in \autoref{alg:cprd}, we identify {\cprd}s based on the two functions.

\begin{algorithm}
    \caption{Happens-After Vector Clocks Builder}
    \label{alg:havc}
    \Fn{\FHAVC{$\HBG$}}{
        \BlankLine
        Initialize $\havc{\NodeV}{\Thread} \gets +\infty$ \hfill $\forall \NodeV \in \Nodes, \Thread \in \Threads$ \;
        \BlankLine
        \ForEach{node $\NodeV$ in $\HBG$ in post-order}{
            \label{alg:havc:mainloop}
            $\havc{\NodeV}{\thread{\NodeV}} \gets \idx{\NodeV}$ \label{alg:havc:initialize} \;
            \BlankLine
            \ForEach{parent node $\NodeParent$ such that $(\NodeParent, \NodeV) \in \HBEdges$}{
                \label{alg:havc:parentloop}
                \ForEach{$\Thread \in \Threads$}{
                    $\havc{\NodeParent}{\Thread} \gets \min \left( \havc{\NodeParent}{\Thread}, \havc{\NodeV}{\thread{\NodeV}} \right)$ \label{alg:havc:update} \;
                }
            }
        }
        \BlankLine
        % \KwRet $\havc{\NodeV}{} \hfill \forall \NodeV \in \Nodes$\;
        \KwRet $\havc{}{}$\;
    } 
\end{algorithm}

\begin{algorithm}
    \caption{Persisted-Before Vector Clocks Builder}
    \label{alg:pbvc}
    \Fn{\FPBVC{$\HBG$}}{
        \BlankLine
        Initialize $\hbvc{\NodeV}{\Thread, \VarX} \gets -\infty$ \hfill $\forall \NodeV \in \Nodes, \Thread \in \Threads, \VarX \in \Vars$ \;
        Initialize $\pbvc{\NodeV}{\Thread, \VarX} \gets -\infty$ \hfill $\forall \NodeV \in \Nodes, \Thread \in \Threads, \VarX \in \Vars$ \;
        \BlankLine
        \ForEach{node $\NodeV$ in $\HBG$ in reversed post-order}{
        
            % RW
            \BlankLine
            \Comment*[l]{Handle Read and Write nodes}
            \If{$\NodeV \in \ReadNodes \cup \WriteNodes$}{
                $\hbvc{\NodeV}{\thread{\NodeV},\var{\NodeV}} \gets \idx{\NodeV}$\;
            }
        
            % F
            \BlankLine
            \Comment*[l]{Handle Flush nodes}
            \If{$\NodeV \in \FlushNodes$}{
                \ForEach{$\Thread \in \Threads$}{
                    $\pbvc{\NodeV}{\Thread,\var{\NodeV}} \gets \hbvc{\NodeV}{\Thread,\var{\NodeV}}$\;
                }
            }
        
            % Pass to children
            \BlankLine
            \Comment*[l]{Handle children nodes}
            \ForEach{child node $\NodeChild$ such that $(\NodeV, \NodeChild) \in \HBEdges$}{
                \ForEach{$\Thread \in \Threads$}{
                    \ForEach{$\VarY \in {\Vars}$}{
                        $\hbvc{\NodeChild}{\Thread,\VarY} \gets \max \left( \hbvc{\NodeChild}{\Thread,\VarY}, \hbvc{\NodeV}{\Thread,\VarY} \right)$\;
                        $\pbvc{\NodeChild}{\Thread,\VarY} \gets \max \left( \pbvc{\NodeChild}{\Thread,\VarY}, \pbvc{\NodeV}{\Thread,\VarY} \right)$\;
                    }
                }
            }
        }
        \BlankLine
        % \KwRet $\pbvc{\NodeV}{} \hfill \forall \NodeV \in \Nodes$\;
        \KwRet $\pbvc{}{}$\;
    }
\end{algorithm}


\begin{algorithm}
    \caption{Concurrent Persistence Race Detector}
    \label{alg:cprd}
    % \newcommand{\DependentNodeVar}{\NodeV}
    \newcommand{\DependentNodeVar}{\NodeWEx}
    \Fn{\FCPRD{$\HBG$, $\PDG$}}{
        $\havc{}{} \gets \FHAVC{\HBG}$\;
        $\pbvc{}{} \gets \FPBVC{\HBG}$\;
        $\races \gets \EmptySet$\;
        \BlankLine
        \ForEach{write node $\DependentNodeVar \in \WriteNodes$ in $\HBG$}{
            \ForEach{read node $\NodeR \in \ReadNodes$ such that $\PD{\DependentNodeVar}{\NodeR}$ in $\PDG$}{
                % TODO: explain that t wasn't changed or something
                \Assert{$\thread{\NodeR} = \thread{\DependentNodeVar}$} \; % \Comment*[r]{The 2 nodes are on the same thread}
                
                \BlankLine
                \Comment*[l]{If the dependent node and the read node are of the same variable, there is not bug}
                \If{$\var{\DependentNodeVar} = \var{\NodeR}$}{
                    \Continue\;
                }
                
                \BlankLine
                \Comment*[l]{If the read node is persisted, there is not bug}
                \If{$\idx{\NodeR} \leq \pbvc{\DependentNodeVar}{\thread{\DependentNodeVar},\var{\NodeR}}$}{
                    \Continue\;
                }

                \BlankLine
                \ForEach{write node $\NodeW \in \WriteNodes$ such that $\var{\NodeW} = \var{\NodeR}$}{
                    \BlankLine
                    \If{$\pbvc{\DependentNodeVar}{\thread{\NodeW},\var{\NodeW}} < \idx{\NodeW} < \havc{\NodeR}{\thread{\NodeW}}$}{
                        $\races \gets \races \cup {(\NodeR, \NodeW)}$\;
                    }
                }
            }
        
        }
        \BlankLine
        \KwRet $\races$\;
    }
\end{algorithm}

The concept of operating systems for coffee machines is not entirely novel. Previous attempts have focused on various aspects of coffee preparation and automation. Here, we provide a brief overview of these endeavors and highlight how ESPLOS improves upon them.



\textbf{PMRace} \cite{pmrace2022} – a NVM bug detector designed for concurrent NVM programs.
Until recently, most works didn’t focus on NVM bugs in concurrent programs, mostly due to the complex search space that thread scheduling introduces.
In ASPLOS 2022, Chen, Zhangyu, et al. introduced PMRace, that focuses on bug detection in concurrent NVM programs. 
PMRace is a fuzzing-based bug detector that is aimed at detecting 2 types of PM bugs:
\begin{itemize}
    \item PM inter-thread inconsistencies – a program execution in which one thread makes durable side effects based on non-persisted data written by another thread. This is the definition of our concurrent persistency race.
    \item PM synchronization inconsistencies - an inconsistency between a persistent synchronization variable (e.g., a lock, a mutex, etc.) and the non-persistent thread state.
\end{itemize}
PMRace detects PM inter-thread inconsistencies by finding all pairs of read/write operations to the same PM addresses (named PM alias pairs). It later simulates a delay after the write operation that allows the read operation to continue and to hopefully introduce the inconsistency bug.

PMRace tries to maximize its coverage of PM alias pairs to detect more bugs. To find the inconsistencies, PMRace detects program dependency relations and sees if an NVM location, that is dependent on the PM alias pair’s data, is modified with un-persisted data.

\paragraph{Witcher} \cite{witcher2021} – a crash consistency bug detector for NVM software that focuses on exploring the NVM state space.
Witcher uses an LLVM pass to trace the program's execution and to detect possible violations of NVM state. It finds likely invariants on the program’s persistence order and tests its correctness by simulating a crash. Later it checks the equivalence of the NVM state with and without the simulated crash and finds NVM violations if the states are different.
Witcher is designed to be scalable (doesn’t suffer from test space explosion), automatic (doesn’t require manual source code annotations), and precise (doesn’t produce false positives).
Witcher doesn’t focus on exploring thread interleaving, and therefore isn’t suited to find difficult concurrency NVM bugs. They leave this for future work.

\paragraph{VSV-D} (Vector Space Verification – Durability) \cite{vsvd2021} – a dynamic analysis tool that checks durable linearizability at runtime.
Requires user annotations – granularity of operations is defined by the user.
Mostly verifies that all required NVM data is guaranteed to be flushed.

\paragraph{XFDetector} (Cross-Failure Detector) \cite{xfdetector2020}
Detects NVM bugs between the pre-failure and post-failure stages, named Cross-Failure Bugs.
These bugs can be categorized into 2 classes:
\begin{itemize}
    \item Cross-failure races – a post-failure operation that relies on data that wasn’t persisted in the pre-failure stage.
    \item Cross-failure semantic bugs – a post-failure operation that reads data that might be persistent but is considered invalid by program semantics.
\end{itemize}

\paragraph{PMTest} \cite{pmtest2019}
Supplies 2 low-level program checkers:
\begin{itemize}
\item isPersist – checks if an NVM memory location is persisted.
\item isOrderedBefore – checks if an NVM memory location is persisted before another location.
\end{itemize}

Using these checkers, the user can assert program invariants and detect inconsistency bugs.

\textbf{Recipe} \cite{recipe2019} an approach for converting concurrent DRAM data structures into crash consistent data structures for persistent memory.

The common conversion step is to insert a cache line flush and memory fence instructions after each store. 
This approach can produce a bug where data that is modified in one thread can be read by another thread before being persisted. This data can later be used to update other NVM locations that might get persisted before the original data persists. If a crash occurs before the original data persists but after the dependent data persists in another thread, an inconsistency bug will occur. The NVM state after the crash is no longer consistent.

In this work we call such bug a Concurrent Persistency Race, and this is the bug that we hope to detect with our bug detector.
